# План улучшения DockTUI

Дата: 2026-10-01.
Репозиторий: https://github.com/strmax195-hue/docktui
Основа анализа: main, коммит 7c5e318c6e32b2cb612aead3af6cdfc65061aff1.
Статус: предложение по развитию; реализация задач в этот запрос не входит.

## Цель и ограничения

Сделать DockTUI надёжным инструментом ежедневной работы с Docker по SSH:
достоверные проверки здоровья, единый выбор хоста для всех операций,
отзывчивый интерфейс и предсказуемое завершение фоновых процессов.

Предположение: нужен общий план улучшений с приоритетами.
Сохранить отсутствие runtime-зависимостей, работу через Docker CLI,
поддержку Linux/macOS/Windows и документированный контракт JSON/exit codes.
Текущий минимум Python — 3.9. Его изменение требует отдельного решения
с учётом поддержки серверных ОС и сроков поддержки самого Python.

Это портфель небольших изменений. Каждый пункт ниже оформлять отдельным PR.
Для крупных новых возможностей сначала уточнять интерфейсы и пользовательские сценарии.

## Что уже есть

- Версия 1.5.0 в main: status/check/doctor/config, Compose, удалённые endpoints,
  логи, exec, массовые действия, работа с images/volumes/networks.
- CI: unit tests на трёх ОС, lint/mypy, интеграция с реальным Docker на Linux.

- Три открытых элемента из issues API являются Dependabot PR: #12, #13, #14.
  Они не являются тремя пользовательскими bug reports.

Проверка выполнена чтением кода, конфигурации CI и метаданных GitHub.
Локальное выполнение приложения и тестов не проводилось.
Ниже риски, найденные статически, отделены от предлагаемых новых функций.

## Подход

Рекомендуемый порядок: надёжность → удобство и поддерживаемость → мониторинг.
Альтернатива с акцентом на новые функции даст больше видимых изменений, но
расширит существующие проблемы выбора хоста и обработки ошибок.
Полная смена TUI-стека противоречит текущей ценности dependency-free и потребует
миграции уже большого набора функций. Сначала достаточно точечных улучшений.

## Этап 1 — достоверность и корректность, P0

### 1. Не выдавать сбой Docker за пустой успешный результат

Основание: docktui/docker_client.py:248–304 возвращает [] / {} при ошибке ps/stats;
docktui/cli.py:cmd_check после предварительного ping не проверяет успешность
сбора данных; report.overall_level([]) возвращает 0.
Если ping прошёл, а ps затем завершился ошибкой, без --require возможен ложный OK.

Файлы: docktui/docker_client.py, docktui/cli.py, docktui/report.py,
tests/test_docker_client.py, tests/test_cli.py, tests/test_report.py.

- [ ] Разделить «успешный пустой список» и ошибку команды через явный результат
  или типизированную ошибку; согласовать подход для методов получения ресурсов.
- [ ] Ошибки обязательного сбора данных в check возвращают UNKNOWN/3.
  Если заданы пороги CPU/memory, сбой получения нужных stats тоже даёт UNKNOWN.
- [ ] status возвращает ненулевой код при невозможности собрать snapshot.
  TUI сохраняет последний успешный snapshot с пометкой о давности и ошибке.
- [ ] Добавить регрессии: daemon доступен, ps падает; ps истекает по timeout;
  stats падает при --cpu-warn; реально пустой успешный ps остаётся корректным.
- [ ] Проверить текст, --json и --quiet; JSON на ошибке должен быть валидным,
  а quiet не должен печатать служебные сообщения.

Готово: указанные ошибки никогда не маскируются кодом 0.
Оценка: 2–3 рабочих дня.

### 2. Единый хост для snapshot, logs, pull и interactive exec

Основание: DockerClient._run передаёт _env(), но LineStreamer.start не принимает env,
а run_interactive_exec вызывает subprocess.run(cmd) без env.
DockerClient.__init__ также изменяет глобальный os.environ при host.
После set_host потоковые и интерактивные команды могут обращаться к другому daemon.

Файлы: docktui/docker_client.py, docktui/log_stream.py, docktui/tui.py,
docktui/cli.py, tests/test_docker_client.py, tests/test_log_stream.py,
tests/test_tui_state.py, tests/test_cli.py.

- [ ] Передавать неизменяемый снимок окружения подключения всем subprocess:
  обычным, streaming и интерактивным.
- [ ] Устранить глобальную запись DOCKER_HOST из конструктора клиента;
  явно передавать окружение тем операциям, которые раньше полагались на неё.
- [ ] Определить единый приоритет: явный -H → окружение Docker →
  выбранный endpoint конфигурации → текущий context. Учесть DOCKER_CONTEXT
  и проверять фактический daemon, а не только строку заголовка.
- [ ] Применять config.active_endpoint одинаково в TUI/status/check/doctor;
  неизвестное имя явно диагностировать.
- [ ] При смене хоста останавливать старые стримы, сбрасывать связанные данные
  и не принимать результаты старых запросов.
- [ ] Тестировать два клиента для разных хостов в одном процессе, переключение
  endpoint A→B, logs/pull/interactive exec и неизменность os.environ.

Готово: все команды выбранного endpoint получают одно и то же подключение;
данные предыдущего хоста не попадают в новый экран.
Оценка: 2–4 дня. Выполнить до multi-host проверок.

### 3. Исправить построение Compose-команд

Основание: run_compose_cmd в docktui/docker_client.py:942–968 строит
docker -f FILE compose ... или docker -p PROJECT compose ...
В Compose CLI эти опции должны следовать после compose.

Файлы: docktui/docker_client.py, docktui/tui.py,
tests/test_docker_client.py, .github/workflows/tests.yml.

- [ ] Строить docker compose -p PROJECT -f FILE1 -f FILE2 ACTION.
  Передавать project name и при наличии файлов.
- [ ] Сохранить порядок нескольких Compose-файлов; проверить cwd и доступность
  конфигурации на машине, где запускается CLI.
- [ ] Для удалённого daemon явно сообщать, если путь из labels существует
  только на удалённом сервере. Не запускать другую локальную конфигурацию молча.
- [ ] Разделить короткие операции и длинные build/up по timeout и отображать
  прогресс длинных операций.
- [ ] В CI на изолированном проекте проверить up, restart, build и down;
  cleanup выполнять даже при сбое теста.

Готово: реальные lifecycle-команды проходят на тестовом Compose-проекте;
отсутствующие файлы дают понятную ошибку.
Оценка: 1–2 дня.

### 4. Ограничить память и исправить завершение streaming-процессов

Основание: LineStreamer._lines растёт без ограничения даже при ограниченном
dashboard.log_lines. on_stop вызывается из stop(), а не при естественном
завершении. Для pull это мешает различать успех, ошибку и отмену.
Финальный блок TUI завершает logs и refresh, но не pull_streamer.

Файлы: docktui/log_stream.py, docktui/tui.py, tests/test_log_stream.py,
tests/test_tui_state.py.

- [ ] Ввести ограниченный буфер deque с явно заданным лимитом;
  исключить ненужное дублирование истории в streamer и TUI.
- [ ] Событие завершения должно приходить один раз и содержать returncode
  и признак отмены; естественный выход также должен его вызывать.
- [ ] Закрывать pipes, дожидаться процесса после kill и завершать reader threads.
  Проверить дочерние SSH-процессы на поддерживаемых ОС.
- [ ] При выходе закрывать logs, pull и refresh; при ошибке показывать причину.
- [ ] Проверить поток из 100000 строк с лимитом 500: сохранено ровно
  последних 500 строк; повторный stop безопасен.
- [ ] Проверить exit 0, exit 1, cancel, EOF, невозможность запуска и выход TUI
  во время pull; callback завершения в каждом случае ровно один.

Готово: объём истории ограничен и процессы не остаются после выхода;
pull отображает фактический результат.
Оценка: 2–3 дня.

## Очерёдность и оценка

1. P0: 7–12 рабочих дней. Сначала регрессии, затем исправления и patch release.
2. P1: 12–18 дней. Очередь задач, выделение модулей, config и выпуск.
3. P2: 10–14 дней. Каждую функцию выпускать отдельно после проверки спроса.

Оценки ориентировочные для одного разработчика, знакомого с Python/Docker;
не включают ожидание внешних доступов, review и поддержку новых платформ.
P0/P1 занимают примерно 4–6 рабочих недель. Весь список — 6–9 недель.

## Проверки перед каждым PR

Для задач кода: сначала регрессионный тест на исходном поведении, затем
минимальное исправление, целевые tests и общий pytest/ruff/mypy.
Для Compose и подключения нужны также интеграционные проверки изолированных
ресурсов. Публикация проверяется установкой собранного wheel, а не editable install.

Команды после подготовки checkout и dev-окружения:
- pytest tests/
- ruff check .
- ruff format --check .
- mypy
- python -m build
- python -m twine check dist/*

Сборка обязательна для release/packaging изменений.
Не считать зелёный текущий CI доказательством устранения найденных выше рисков.

## Самопроверка плана

- Найденные P0 проблемы имеют адресуемые файлы, сценарии регрессии и критерии готовности.
- Новые функции зависят от корректного контракта ошибок и подключения.
- Не предлагаются уже существующие функции как новые.
- Сохраняются dependency-free подход и Docker CLI.
- Оценки отделены от фактов; локальные тесты не объявлены пройденными.
